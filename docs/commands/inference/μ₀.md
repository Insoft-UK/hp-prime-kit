## Behaviour

**Both rows are the name as HP's list spells it, and both are refused**
(emulator). They were taken in two different batches, one with the Function
app active and one with the Inference app active, so this is not the app
rule: every other variable of this group answered in the second of those
batches.

**The same two glyphs with a different codepoint answer 0.5** (emulator).
HP's list uses GREEK SMALL LETTER MU, U+03BC; the calculator answers to MICRO
SIGN, U+00B5. On screen they are the same shape. That row is stored under the
name that works, which is why it is not in the table above -- an entry's
examples are rows for the entry's own name, and these two names are not the
same name. The fact is
[ppl.mu-zero-spelling](../../topics/ppl.md#ppl.mu-zero-spelling).

**Eleven of the twelve Greek and subscripted names in this group answered as
listed** (emulator): π₀, σ₁, σ₂, n₁,
n₂, s₁, s₂, x₁, x₂, Mean₁ and Mean₂. So
this is one name's spelling and not a rule about non-ASCII names -- which the
first batch of this phase could not tell apart, because everything in it
refused for want of the right app.

**0.5 is the null-hypothesis value the app arrived with** (emulator), the
same number [π₀](π₀.md) holds, and a default rather than
anything measured from data.

**This entry keeps the spelling that does not work** (HP help). The title has
to match the list, and `docs/commands/names.tsv` is generated from HP's
Command Tree rather than edited by hand. A program should use the other one.

## Models get wrong

| They write | What happens | Seen in |
|---|---|---|
| μ₀ with GREEK SMALL LETTER MU | refused, and it is what HP publishes | [emulator](../results.tsv) |
| µ₀ with MICRO SIGN | answers 0.5, and the linter calls it invented | [emulator](../results.tsv) |

The interpreter does not implement it, so `hpprime run` cannot check a program
that uses it (unverified).
