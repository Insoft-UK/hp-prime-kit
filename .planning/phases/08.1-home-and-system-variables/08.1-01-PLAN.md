<context>
@.planning/phases/08.1-home-and-system-variables/08.1-CONTEXT.md

The batch is built by a script kept outside the repository, like every probe
list before it, and generated against the stored keys: no call repeats a
stored one, and none repeats within the batch. It lints with no finding.

How the batch is shaped:

- **Reads**: each name inside `EXPR`, so a name that refuses costs its row.
- **Can a program set it**: a function body that reads the value, assigns it
  back or sets another, reads again, and puts the first value back, all in
  one row.
- **What a setting changes**: the same body, measuring inside the row --
  `SIN(90)` under `HAngle`, `(-4)^0.5` under `HComplex`, `STRING(R→B(255))`
  under `Base`, `STRING(1/3)` under `HFormat` and `HDigits`,
  `STRING(1234.5)` under `HSeparator` -- so no later row is read in another
  format.
- **`Ans`**: read, then `EXPR("2+3")`, then read again: whether `EXPR` in a
  program moves it.
- **`GET`**: bare, `GET(1)` and `GET(QPI(0.5))`, the last because the release
  note that names it is about `QPI`'s answers. `GET("A")` is not tried: a
  string inside a string in `EXPR` needs a quote nobody here has measured how
  to write.
- **Question 7**: a list and a matrix indexed with a 0 held in a variable,
  so the program compiles whatever the answer; and the same 0 assigned to.
- **Questions 13 and 14**: `MOD` and `NTHROOT` with `+`, `*` and `^` on
  either side, each chosen so the two possible bindings give different
  answers, and with negative operands.
- **Question 15**: `alog(2)`, `Alog(2)` and `xpon(1000)`, names that exist on
  HP's list only in upper case and are not CAS names, against `ALOG(2)`.
</context>
